# TeemoBKK 작업 하네스 운영 기준

상태: 운영 초안. 기존 작업·설정·예약·게시 경로를 자동으로 바꾸지 않는다.

## 목적과 도구 경계

- Hermes Kanban은 이 Hermes 설치에서 세션 간 업무 상태를 기록하는 단일 작업 원장이다.
- GitHub는 코드, 커밋, 검토 요청의 기준이다. Kanban과 GitHub에 같은 업무 상태를 따로 관리하지 않는다.
- Kanban은 이 Hermes 호스트의 로컬 SQLite 보드다. 다른 호스트와 자동 동기화되지 않는다.
- 외부 작업자가 Kanban을 직접 읽거나 쓸 수 있다고 가정하지 않는다. 연결과 권한을 각 작업자 실행 환경에서 검증하기 전까지 티모가 접수·상태 기록을 맡는다.
- 같은 작업은 활성 구현 담당자 한 명만 둔다. 검토자는 구현 파일을 수정하지 않는다.
- Git branch/worktree는 파일 변경을 나누는 수단이지 OS 보안 경계가 아니다. 구현자에게 운영 자격 증명이나 불필요한 민감 자료를 노출하지 않는다. 신뢰하지 않는 작업자를 격리해야 하면 별도 OS 계정·컨테이너·권한 및 네트워크 제한을 먼저 마련하고, 그렇지 못하면 해당 작업자를 배정하지 않는다.
- Kanban `review`는 업무 흐름의 검토 단계이고 GitHub PR review는 코드 검토 증거다. 두 상태를 서로 대신하는 것으로 취급하지 않는다.

## 역할

| 역할 | 책임 | 권한 경계 |
| --- | --- | --- |
| 주인님 | 우선순위, 범위, 운영 게시·배포 승인 | 운영 반영과 공개 동작의 최종 승인 |
| 티모, 조정자 | 요청 정리, 카드 관리, 작업 격리, 진행·증거 추적, 통합 판단 | 승인 범위를 넓히지 않으며 불명확하거나 위험하면 중단 |
| 구현자 | 지정 브랜치/worktree 안에서 한 작업 구현 및 검사 | 다른 작업공간, 운영 서버, 자격 증명, 게시·배포를 건드리지 않음 |
| 검증자 | 변경 범위와 완료 기준을 독립 검사 | 검증 의견을 남기며 구현자 대신 통합·배포하지 않음 |
| 운영자 | 승인된 통합·게시·배포 실행과 사후 확인 | 대상 커밋·환경·복구 계획이 확인되고 별도 승인된 경우만 실행 |

외부 에이전트의 등록, 온라인 표시, 도구 검색 성공은 실제 작업 수행 능력이나 자원 접근 권한의 증거가 아니다. 한 번의 제한된 비운영 시험에서 요청·응답·결과물·검증 근거를 확인한 뒤 역할을 부여한다.

## 작업 카드 기준

모든 신규 업무 카드는 다음 항목을 갖춘다.

```text
목표:
담당자와 역할:
우선순위와 선행 조건:
범위:
제외 범위와 금지 행동:
기준 브랜치와 시작 커밋:
작업 worktree:
완료 조건:
검사 명령과 예상 결과:
필요한 승인:
승인자·시각·정확한 행위·대상/환경·범위·승인 근거 참조:
산출물과 증거 위치:
현재 막힘과 다음 행동:
```

완료 기준은 확인 가능한 결과로 쓴다. 예를 들어 테스트 이름·실제 URL·게시 ID·대상 브랜치처럼 읽어 확인할 수 있는 근거를 지정한다. 비밀번호, 토큰, 쿠키, 개인 키, 인증 코드, 불필요한 개인 정보는 카드·댓글·로그에 넣지 않는다.

## 상태 흐름

- `triage`: 요청은 접수했지만 요구나 담당을 정리하는 중.
- `todo`: 범위와 완료 조건은 있으나 아직 시작 전.
- `ready`: 검증된 담당자와 안전한 실행 경로가 정해져 작업을 시작할 수 있음.
- `running`: 담당자가 할당된 작업공간에서 실행 중. OS 수준의 격리는 별도로 확인한다.
- `review`: 구현이 끝나 독립 검증을 기다림.
- `done`: 완료 조건과 검증 증거가 모두 확인됨.
- `blocked`: 사용자 입력, 권한, 의존성 또는 환경 문제로 진행을 멈춤. 이유와 재개 조건을 적는다.
- `archived`: 보존할 이력을 남기고 활성 보드에서 치운 작업. 삭제나 과거 기록 일괄 정리를 뜻하지 않는다.
- `scheduled`: 공식 문서의 기본 상태 집합에는 없는 CLI 확장이다. 이 초안 작성 환경의 Hermes Agent v0.21.5에서는 `hermes kanban list --help`에 상태가 표시되고 `hermes kanban schedule --help` 명령이 확인됐다. 다른 버전에서 지원된다고 가정하지 않는다.

`scheduled`를 쓰기 전 현재 CLI에서 `hermes kanban list --help`에 상태가 있고 `hermes kanban schedule --help`가 동작하는지 확인한다. 둘 중 하나라도 지원되지 않으면 `blocked`로 두고 댓글에 재개 시각·조건을 적는다. 사람의 승인을 기다리는 작업도 `blocked`로 둔다. 담당자와 승인 범위가 확인되지 않은 카드는 자동 실행 가능한 `ready`로 두지 않는다. 오래 막혀 있다는 경고는 상태를 풀거나 실행할 권한이 아니다. 과거 날짜의 예약·게시를 되풀이하지 않는다.

## 코드 작업 흐름

1. 티모가 현재 카드·저장소·브랜치·작업공간을 확인하고 중복 작업을 찾는다.
2. 각 작업은 전용 브랜치와 Git worktree에서 시작한다. 작업 전에 기준 커밋과 깨끗한 상태를 기록한다.
3. 구현자는 작은 논리 단위로 수정하고 해당 범위의 검사를 실행한다. 예상 밖 변경이나 기존 미커밋 변경이 보이면 중단하고 보고한다.
4. 완료 시 변경 파일, 커밋, 실행한 검사와 종료 코드, 실패·미실행 검사를 카드에 기록한다.
5. 구현자는 `hermes kanban request-review`로 카드를 `review`로 옮기고 변경·검증 근거를 인계한다. 별도 검증자는 완료 조건과 diff를 확인하고, 새 실패와 기존부터 있던 실패를 구분한다.
6. 검토 통과와 모든 적용 가능한 완료 조건이 확인된 뒤에만 `hermes kanban complete`로 `done` 처리한다. 검토 미실시, 필수 검사 미실행, 미확인 외부 반영이 있으면 완료 처리하지 않고 막힘이나 남은 위험을 기록한다.
7. 티모가 범위·검증·충돌 여부를 확인한 뒤에만 통합 후보로 올린다. 큰 선행 브랜치는 커밋을 업무별로 분류하고 검사하기 전 일괄 병합하지 않는다.
8. 통합, GitHub 푸시, 운영 배포는 서로 다른 단계다. 한 단계의 완료를 다음 단계 승인으로 보지 않는다.

운영 checkout은 공동 작업용 worktree로 사용하지 않는다. 기존 파일이나 추적되지 않는 운영 변경이 있으면 보존·복구 계획이 확인될 때까지 초기화, 정리, 덮어쓰기 배포를 금한다.

## 승인과 중단 기준

별도 승인 없이는 다음을 하지 않는다.

- 사용자에게 공개되는 글·뉴스·Substack 게시 또는 새 수신자 추가
- 운영 설정, 예약 작업, 서비스 재시작, 데이터베이스 쓰기
- GitHub 푸시, PR 생성·병합, 운영 배포
- 새 MCP·에이전트 설치 또는 외부 에이전트에 코드·운영 자료 전달

대상, 인증, 권한, 변경 범위, 작업 결과 중 하나라도 불명확하거나 테스트 실패·충돌·중복 실행 가능성이 있으면 진행을 멈추고 카드에 막힘과 다음 확인을 기록한다. 성공한 명령 실행만으로 원격 반영·게시·수신을 주장하지 않는다. 각 외부 상태 변경은 정확한 대상에서 읽어 되돌려 확인한다.

승인은 승인자와 시각, 허용된 행위, 정확한 대상과 환경, 범위, 원 요청의 참조를 기록해야 한다. 대상 커밋·게시물·수신자·환경이 바뀌면 기존 승인은 이어지지 않으며 다시 확인한다. 포괄적이거나 과거 세션에서 추정한 승인은 실행 근거로 쓰지 않는다.

## 인계 기록

작업을 넘길 때 카드에 아래를 남긴다.

- 마지막으로 확인한 상태와 시각
- 담당자, 브랜치, worktree, 기준 커밋과 최신 커밋
- 실행한 검사와 실제 결과
- 승인 여부와 승인자·시각·행위·정확한 대상/환경·범위·근거 참조
- 남은 위험·차단 사항
- 다음 한 가지 행동

새 세션은 기록을 읽고 대상 상태를 확인한 뒤 재개한다. 과거 세션의 지시나 보드 카드 자체를 새 승인으로 해석하지 않는다.

## 완료 보고

완료 보고에는 변경 범위, 완료 조건별 확인 결과, 독립 검토 결과, 남은 문제를 적는다. 코드가 아닌 작업도 게시 ID·수신 확인 등 해당 작업의 완료 근거를 지정해 되읽어 검증한다. 푸시·배포·수신 확인은 각각 별도의 증거가 있어야 한다. 확인하지 않은 항목은 미확인으로 표시한다.
